# 플랫폼 결정과 접근성 요건

**작성:** 2026-09-22 · **상태:** 결정 · **전제:** [build-spec.md](build-spec.md) §1, [ops-autonomy.md](ops-autonomy.md) D1·D2

---

## 0. "접근성"을 둘로 나눈다

이 질문은 하나처럼 보이지만 두 개다. 답이 서로 반대 방향으로 당긴다.

| | 질문 | 무엇을 배신하면 실패하나 |
|---|---|---|
| **도달 접근성** | 처음 보는 부모가 **몇 번 만에** 화면에 닿나 | 설치 장벽 → G2에서 아직 못 푼 채널 문제 |
| **사용 접근성 (a11y)** | 닿은 뒤 **누가 못 쓰나** | 대비·글자 크기·색 단독 의미 |

웹은 앞을 이기고, 네이티브 앱은 뒤를 이긴다 — 고 흔히 말하지만 **이 제품에서는 거꾸로다.** 아래가 그 이유다.

---

## 1. 결정

> **Expo (React Native)로 앱을 만들고, 같은 코드베이스에서 `react-native-web`으로 「보여주기」 한 화면만 웹 체험판으로 낸다.**

앱이 제품이고, 웹은 **채널 도구**다. 둘을 따로 만들지 않는다.

| 층 | 선택 | 접근성 관점의 이유 |
|---|---|---|
| 본체 | Expo → iOS · Android | 홈 화면 아이콘 · 오프라인 · 인앱 결제 |
| 체험판 | `react-native-web` 웹 1화면 | 설치 없이 링크 하나로 핵심 장면 체험 |
| 배포 | EAS Build / EAS Update | 1인이 두 스토어를 동시에. JS 수정은 심사 없이 밀어넣음 |

---

## 2. 웹 단독(PWA)을 배제하는 이유 — 세 가지

웹의 도달력은 분명히 우리 약점을 정확히 찌른다. 그런데도 본체가 될 수 없다.

### ① 3초 규칙 — 이 제품은 계산대 앞에서 열린다

사용 장면이 **마트에서 아이가 조르는 그 순간**이다. 부모가 브라우저를 열고 탭을 찾고 있으면 그 순간은 이미 지나갔다. 홈 화면 아이콘이 없으면 제품이 성립하지 않는다.

PWA도 홈 화면에 추가할 수 있지만, iOS Safari에서 **공유 → 홈 화면에 추가**는 앱스토어 설치보다 낯선 동작이다. 도달 장벽을 낮추려고 웹을 고른 뒤, 더 어려운 설치를 시키는 셈이 된다.

### ② 오프라인 — 이미 명세에 쓴 제약이다

build-spec.md §1: *"오프라인 동작이 필수다. 보여주기는 마트에서 쓰인다."* 지하 주차장·대형마트 안쪽은 신호가 약하다.

서비스워커로 캐시할 수는 있으나 **iOS는 미사용 PWA의 저장소를 축출한다.** 주 1~2회 쓰는 우리 제품은 정확히 그 축출 대상이다. 목표 사진이 사라진 채로 열리는 앱은 이 제품에서는 빈 껍데기다.

### ③ 결제 — D2가 무너진다

D2는 *"앱스토어 인앱 구독만"*이고, 이건 자율 운영 설계의 **기둥**이다. 웹이면 결제·환불·세금이 전부 나에게 온다.

MoR(Paddle·Lemon Squeezy)를 쓰면 세금과 환불을 대행하므로 수수료는 오히려 싸다(약 5% vs 앱스토어 15%). 하지만 **환불 문의 메일은 여전히 나에게 도착한다.** 유료 235명이 손익분기인 규모에서 이 한 축이 주 0.93시간을 넘긴다.

> 정리: 웹의 도달력은 매력적이지만, 그걸 얻으려면 **오프라인·즉시성·무인 결제**를 동시에 내려놔야 한다. 그 셋은 각각 명세에 못 박힌 제약이다.

## 3. 그래서 웹을 버리지는 않는다 — 체험판으로 쓴다

채널이 G2의 미해결 과제로 남아 있다(카드 없이 유기적으로 100만을 모은 사례 0건). **설치를 요구하는 순간 깔때기에서 대부분이 샌다.**

그래서 웹은 이렇게 쓴다:

```
커뮤니티 글 · 광고
   → 링크 클릭 (설치 0)
   → 샘플 데이터로 「보여주기」 화면이 바로 뜬다 — 슬라이더도 움직인다
   → "우리 아이 걸로 만들기"
   → 앱스토어
```

체험판에 있는 것: **보여주기 화면 하나**, 슬라이더, 3주→4주 전환, 샘플 목표 사진.
체험판에 없는 것: 계정, 저장, 사진 업로드, 정산.

**실험 2(채널 탐침)를 이 체험판으로 돌린다.** 랜딩의 "관심 있어요" 클릭보다 훨씬 강한 신호다 — 슬라이더를 끝까지 움직여 본 사람은 개념을 이해한 사람이다.

`react-native-web`이므로 **화면을 두 번 만들지 않는다.** 이게 Expo를 고르는 두 번째 이유다.

## 4. 탈락시킨 선택지

| | 왜 아닌가 |
|---|---|
| **네이티브 2벌** (Swift + Kotlin) | 1인 12주에 두 플랫폼은 불가능. 접근성 API는 가장 좋지만 그걸 쓸 시간이 없다 |
| **Flutter** | ① 자체 캔버스 렌더링이라 플랫폼 접근성 트리를 **번역해서** 붙인다 — 동적 글자 크기와 스크린리더가 RN보다 한 겹 멀다. ② Flutter Web은 캔버스라 링크 체험판의 초기 로딩·SEO가 나쁘다 — §3 전략과 정면으로 충돌 |
| **웹 단독 (PWA)** | §2 |
| **카카오톡 채널 / 챗봇** | 한국 한정. 글로벌 서비스 전제와 충돌 |

## 5. a11y — 누가 못 쓰나

**중요한 전제: 아이 쪽은 일반 a11y 대상이 아니다.** 아이는 자기 기기로 로그인하지 않는다(build-spec §8). 부모 폰을 건네받아 **한 화면만** 본다. 그래서 아이 쪽 요건은 스크린리더가 아니라 **글을 못 읽어도 읽히는가**이고, 이건 숫자·사진·막대 설계로 이미 답했다.

a11y 요건은 대부분 **부모 쪽**에 걸린다.

### 5.1 색 대비 — 실측 결과, 2건 실패

목업 팔레트를 WCAG 2.1 상대휘도로 계산했다(추정 아님).

| 조합 | 실측 | 판정 |
|---|---|---|
| 본문 `#2B2620` on 크림 `#F7F2E8` | 13.44:1 | 통과 |
| 남색 `#1F4062` on 사진바탕 `#E3D6BE` | 7.43:1 | 통과 |
| 보조 `#6B6153` on 박스 `#EFE6D6` | 4.90:1 | 통과 |
| 빨강 `#C8322C` on 크림 | 4.77:1 | 통과 |
| 빨강 `#C8322C` on 박스 `#EFE6D6` | 4.30:1 | **큰 글씨에서만 합격** |
| 흐림 `#8A7B66` on 크림 | 3.69:1 | **11px에 쓰면 실패** |
| 흐림 `#A3947C` on 사진바탕 | 2.06:1 | **실패** |

마지막 줄이 심각하다. 사진 위 **"아직 못 모은 만큼"** 라벨이다 — 진행바의 의미를 설명하는 유일한 텍스트인데 거의 안 보인다.

**정정 지시 (목업·구현 양쪽):**

| 쓰임 | 현재 | → | 실측 |
|---|---|---|---|
| 사진 위 보조 라벨 | `#A3947C` | **`#5C5347`** | 5.26:1 |
| 11px 흐림 텍스트 전부 | `#8A7B66` | **`#6B6153`** | 5.44 / 4.90:1 |
| 작은 글씨 빨강 | `#C8322C` | **`#B82B26`** | 4.97:1 |
| **큰 숫자 빨강 (4주, 화살표)** | `#C8322C` | 유지 | 큰 글씨 기준 통과 |

### 5.2 동적 글자 크기 — 현재 설계의 실질 위험

부모가 30~40대라도 **iOS Dynamic Type / Android 글꼴 크기**를 키워 쓰는 사람이 적지 않다.

현재 목업은 **390×844 고정 높이**에 `margin-top: auto`로 하단을 밀어붙인 구조다. 글자 배율 130%만 되어도 하단 버튼이 화면 밖으로 나간다.

**요건:**
- `allowFontScaling`을 **끄지 않는다** (RN에서 레이아웃 깨짐을 막으려고 끄는 게 흔한 유혹이다)
- 보여주기 화면을 **`ScrollView`** 로 감싼다 — 단, 상단 사진 진행바 + 3주→4주 블록은 **배율 200%에서도 첫 화면에 함께 보여야 한다**. 이 둘이 동시에 안 보이면 인과가 끊긴다
- 대신 하단(부모 대사, 「샀어요」/「닫기」)은 스크롤 아래로 내려가도 된다
- `maxFontSizeMultiplier`는 **큰 숫자에만** 건다(2.0). 숫자가 화면을 다 먹으면 안 된다

### 5.3 색 단독 의미 금지 — 현재 설계는 통과

"이만큼 되돌아가" 구간이 빨강이지만, **줄무늬 텍스처 + 실선 경계 + 라벨 텍스트**를 함께 쓴다. 적록색약에서도 구분된다. 이 설계를 유지한다.

**금지:** 진행바에서 색만으로 "모은 만큼/못 모은 만큼"을 가르는 것. 경계선과 라벨이 항상 함께 간다.

### 5.4 터치 타깃

슬라이더 손잡이가 현재 30px. **최소 44×44pt**(iOS HIG) 로 히트 영역을 넓힌다 — 시각적 원은 30px을 유지하고 투명 패딩으로 늘린다. 마트에서 한 손으로, 아이가 팔을 잡아당기는 중에 조작된다.

### 5.5 스크린리더 — 범위를 좁힌다

전 화면 VoiceOver/TalkBack 완전 대응은 12주 POC에 넣지 않는다. 대신:

- 모든 **이미지·아이콘에 `accessibilityLabel`** 을 단다(빈 값이라도 명시적으로)
- 슬라이더는 `accessibilityRole="adjustable"` + 값 변경 시 "2000원, 4주" 형태로 읽히게 한다
- **목표 사진은 `accessibilityLabel`을 부모가 입력한 목표 이름으로** 채운다

이 셋이 POC 범위다. 그 이상은 실사용자가 요청하면 그때 한다 — 그렇게 적어두는 것이 정직하다.

## 6. 하지 않는 것

| | 왜 |
|---|---|
| PWA와 네이티브 앱 양쪽 유지 | 1인 운영에서 배포 경로가 둘이면 버그도 둘 |
| 웹 체험판에 로그인·저장 | 체험판이 제품이 되면 §2의 세 문제가 그대로 따라온다 |
| 태블릿 전용 레이아웃 | 사용 장면이 마트다. 폰이 전부 |
| 다크 모드 | POC 범위 밖. 크림색 팔레트를 다크로 옮기려면 대비를 전부 다시 잰다 |

## 부록: 대비 재현

```python
def lum(h):
    h=h.lstrip('#'); r,g,b=[int(h[i:i+2],16)/255 for i in (0,2,4)]
    f=lambda c: c/12.92 if c<=0.03928 else ((c+0.055)/1.055)**2.4
    return 0.2126*f(r)+0.7152*f(g)+0.0722*f(b)
def cr(a,b):
    l1,l2=sorted([lum(a),lum(b)],reverse=True); return (l1+0.05)/(l2+0.05)
```

기준: WCAG 2.1 AA — 일반 텍스트 4.5:1, 큰 텍스트(18.66px 이상 굵게 / 24px 이상) 3.0:1.
