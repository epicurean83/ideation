# 원가 모델 (CPU_월) — kids-economy

작성일: 2026-09-17 · 단계: S2 · 대상 설계: V1+V4 저학년판 (현금 기반, 카드 발급 없음, 장면 S1·S2·S5)
합격선: **녹색 ≤30원 / 황색 30~100원 / 적색 >100원** (활성 사용자 1인당 월 원가)
환율: **1 USD = 1,400원** `[Assumption — 2026-09 기준, 분기별 재확인]`

---

## 1. 활성 사용자 정의

한 가구에 부모 계정 1 + 아이 계정 1이 붙는다. 원가는 가구 단위로 발생하고 RAU는 사람 수로 센다.

| 세는 법 | 가구당 활성 | 비고 |
|---|---|---|
| **보수(기본값)** | **1.0명** (부모만) | 아이가 앱을 안 열어도 성립. **CPU가 가장 높게 나오는 가정** |
| 낙관 | 2.0명 (부모+아이) | 아이가 월 1회 이상 조회할 때 |

**아래 계산은 전부 보수 가정(가구=1인)을 쓴다.** 이 값이 녹색이면 낙관에서는 절반이다.

---

## 2. 가구당 월 사용량 추정

저학년·현금 기반이라 이벤트가 적다. 이것이 이 설계의 원가 구조상 최대 강점이다.

| 이벤트 | 월 빈도 | 산출 근거 |
|---|---|---|
| 주간 배분 입력 (S1) | 4.3회 | 저학년 주 단위 지급 67% |
| 지출 기록 (부모 입력) | 12회 | 주 2~3건 × 4.3주 |
| 위시리스트 등록·해제 (S2) | 4회 | 월평균 용돈 31,678원 규모에서 |
| 주말 돌아보기 (S5) | 4.3회 | |
| 단순 조회 (앱 열기) | 22회 | 부모 주 3회 + 아이 주 2회 |
| **API 호출 합계** | **~50회** | 여유를 두어 **100회**로 계산 |
| 저장 레코드 | ~25건 × 200B = **5KB/월** | 3년 누적 180KB/가구 |
| 푸시 알림 | ~10건 | 배분일 1 + 대기 만료 4 + 주말 4 + 기타 1 |

> **결제 연동이 없다는 점이 여기서 값을 한다.** 카드 기반이면 거래 웹훅·정산 대사·이상거래 탐지가 붙고 호출량이 한 자릿수 배로 뛴다.

## 3. 부품별 단가와 계산식

### 100만 가구 시점

| 부품 | 계산식 | 월 원가 | 신뢰도 |
|---|---|---|---|
| **컴퓨트 (서버리스 API)** | 1억 요청/월. Cloudflare Workers $5 기본 + 초과 100만 요청당 $0.30 → 약 $27, 여유 포함 **$50** | **7만원** | `[Assumption]` 단가 공개값 기반, 실측 필요 |
| **데이터베이스** | 월 1억 쿼리 + 누적 180GB. 서버리스 Postgres 기준 스토리지 180GB × $0.25 + 쿼리 컴퓨트 → **$600** | **84만원** | `[Assumption]` **가장 불확실한 항목.** 아키텍처 의존 |
| **오브젝트 스토리지** | 180GB × $0.015/GB (R2급) = $2.7 | **0.4만원** | `[Assumption]` |
| **목표 사진** | ~~가구당 1~2장 × 150KB~~ → **2026-09-22 설계 변경: 기기 내 저장, 서버 업로드 없음**([ops-autonomy.md](../04-product/ops-autonomy.md) D1). 스토리지·모더레이션 모두 소멸 | **0원** | 설계 결정 |
| **푸시 알림** | FCM 무료 티어 | **0원** | High |
| **인증** | 자체 구현 또는 DB 내장 Auth. 외부 IDaaS는 MAU 과금이라 **쓰지 않는다** | **0원** | 설계 결정 |
| **대역폭·CDN** | 정적 자산 캐시 우선 | **7만원** | `[Assumption]` |
| **생성형 모델 (월 1회 요약)** | 아래 별도 절 | **210만원** | Medium (단가는 공식) |
| **합계** | | **≈ 308만원 / 월** | |

**CPU_월 = 308만원 ÷ 100만 = 약 3.1원** → **녹색** (낙관 가정이면 1.5원)

### 생성형 모델 호출 — 설계를 가르는 항목

단가: **Claude Haiku 4.5 — 입력 $1.00 / 출력 $5.00 per MTok**, Batch API **50% 할인**.

| 설계안 | 호출 빈도 | 가구당 월 원가 | 100만 가구 월 | 판정 |
|---|---|---|---|---|
| **A. 월 1회 요약, 배치** ✅ | 월 1회 · 입력 1,500 + 출력 300 토큰 | (0.0015 + 0.0015) × 0.5 = **$0.0015 = 2.1원** | **210만원** | **채택** |
| B. 주 1회 요약, 배치 | 월 4.3회 | 9.0원 | 903만원 | CPU 10원 — 아직 녹색이나 총액이 3배 |
| C. 지출 기록마다 실시간 호출 | 월 12회 · 배치 할인 없음 | **13.4원** | 1,344만원 | CPU의 **절반 이상**을 한 항목이 먹는다 |
| D. S2 "못 사는 건 뭐야" 매번 생성 | 월 4회 · 실시간 | 4.5원 | 448만원 | 불필요 — 아래 |

**설계 고정 (Kill Rule 2 대응):**

- **S2의 질문과 S6 사기 카드는 사전 생성 + 규칙 기반.** 6~9세에게 던지는 질문은 한 문장이고 변주가 적다. 매번 모델을 부를 이유가 없다
- **주간 돌아보기(S5)도 템플릿 + 규칙 기반.** "이번 주 가장 많이 쓴 곳", "모을 돈이 목표의 몇 %" 같은 집계는 SQL이 한다
- **모델은 월 1회 요약에만, 그것도 Batch API로.** 실시간 경로에 모델을 두지 않으면 지연·실패·재시도 처리도 함께 사라진다

## 4. 규모별 곡선

| 규모 | 월 총 원가 | CPU_월 | 비고 |
|---|---|---|---|
| **1만 가구** | ~30만원 | **30원** (황색 경계) | 고정비(최소 인스턴스·기본요금)가 지배. 무료 티어 안에 들면 0에 가까움 |
| **10만 가구** | ~60만원 | **6원** | 고정비가 분산되기 시작 |
| **100만 가구** | ~308만원 | **3.1원** | 모델 호출이 총액의 68%를 차지하는 구조로 바뀜 |

작은 규모에서 CPU가 높은 것은 정상이다 — 고정비가 나뉘지 않기 때문이고, 사용자가 늘수록 내려간다. **원가가 사용자 수에 선형 이하로 붙는다**는 뜻이므로 Kill Rule 1·2 관점에서 건강한 모양이다.

## 5. 유지비와 유지 배수

| 항목 | 값 |
|---|---|
| 100만 가구 월 유지비 | **약 308만원** |
| 유지 배수 1.0에 필요한 RPU_월 | **3.1원/사용자** = 연 **37원** |
| 참고: 대형 미디어 1인당 연 매출 천장 | 2,000~4,500원 |
| 필요액이 그 천장에서 차지하는 비율 | **약 1~2%** |

> **원가는 이 사업의 문제가 아니다.** 연 37원은 후원·스폰서 1~2건·소수 유료 전환 어느 쪽으로도 덮을 수 있는 높이다.
> 문제는 여전히 **도달**이다 — 100만이라는 분모가 서지 않으면 이 표 전체가 무의미하다.

## 7. 실측 계획 (POC에서 교체할 값)

추정치를 실측으로 바꾸는 것이 S3의 절반이다. 아래 넷은 반드시 잰다.

| # | 실측할 값 | 방법 | 지금 값의 불확실성 |
|---|---|---|---|
| 1 | **DB 쿼리 비용** | POC 4주간 실제 쿼리 수·컴퓨트 시간 계측 | **가장 큼.** 추정 84만원이 2배 이상 틀릴 수 있다 |
| 2 | 가구당 실제 API 호출 수 | 서버 로그 | 100회는 여유를 둔 값. 실제는 더 적을 가능성 |
| 3 | 월 요약 입력 토큰 길이 | `count_tokens`로 실제 기록 길이 측정 | 1,500토큰은 가정 |
| 4 | 가구당 활성 사용자 수 | 아이 계정 월 1회 이상 열람률 | 1.0 vs 2.0이 CPU를 2배 가른다 |

**재계산 규칙:** 설계가 바뀔 때마다 이 파일을 같이 고친다. 특히 모델 호출·저장·트래픽이 늘어나는 변경은 이 표를 먼저 통과해야 한다.
